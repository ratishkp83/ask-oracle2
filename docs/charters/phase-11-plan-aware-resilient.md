> **End goal this phase advances:** *"fully intelligent + cascading reporting."* Phases 8–10 made the product excellent at *proposing*, *answering*, *drilling*, and *delivering*. Phase 11 attacks the next real-world wall: on a client's **real** database — many tables, complex joins, millions of rows, calculation-heavy questions — the generated query is not consistently **accurate or fast**, and a genuinely heavy query **times out the synchronous request**. This phase makes generation **plan-aware** (writes queries that exploit what the client DB already has) and execution **resilient** (a long query no longer fails — it runs as a job). The **semantic/metrics layer** (curated entities + named metrics) is the strategic centerpiece for calculation-heavy output and is deliberately deferred to **Phase 12**, because it lands best once profiling + plan-aware generation exist.

## Why now — the real-life challenge (owner-raised, 2026-06-17/18)
The owner surfaced the live failure mode directly: *"there are scenarios where the query is complex and the query itself times out."* We reviewed an external recommendation (a list of timeout fixes + the metadata gaps that would make NL→SQL effective) **against our actual constraints** and found:

- **~Half of the classic timeout playbook does not apply to us** — we cannot create indexes, materialized views, or partitions on the client's database (read-only, [ADR-009](../adr/ADR-009-readonly-db-account-precondition.md); no schema control). Those fixes invert into **detect-and-exploit** (use the indexes/partitions/stats that already exist) plus an **app-side result cache** (the only "pre-aggregation" we own).
- **The most-cited accuracy trick — feeding the model distinct column values** (so it writes `status = 'A'` not `'Active'`) — **directly violates Invariant 3** (no row data to any model) and is blocked by our redaction tripwire. It needs an invariant-safe redesign (resolve literals **locally**).
- **The one item that actually handles "the query itself times out"** — run it as an **async job** instead of a synchronous request — was buried at the bottom of the recommendation. It is the architectural heart of this phase.

## Context — grounding facts (verified in the code, 2026-06-18)
- **Schema model already carries join material:** `src/schema.py` (`ColumnDefinition.is_primary_key/is_foreign_key/references_table/references_column`, `RelationshipDefinition`); `to_compact_markdown()` already emits a **"Relationships:"** section, so the external prompt **already** conveys FK joins **when the saved schema has them**.
- **Introspection already reads PK/FK** from `ALL_CONSTRAINTS`/`ALL_CONS_COLUMNS` (`src/core/introspection.py`, SELECT-only through the chokepoint), and **degrades gracefully** (warns, continues) when constraint views aren't visible to the account. **It does NOT yet read indexes, partition keys, row counts, nullability detail, or cardinality.**
- **Two real limits today:**
  - `build_external_context()` (`src/core/llm/redaction.py:29`) **truncates the schema at 12 000 chars** → on a large schema, tables are silently dropped and the model loses exactly the join context it needs.
  - Real Oracle schemas (EBS, warehouses) frequently declare **no FK constraints** — joins are by convention — so the introspected join graph is often **empty even where joins exist**.
- **The SQL is already parsed into a sqlglot AST** at the chokepoint (`src/core/sql_safety.py:99`, Oracle dialect) — but only to prove *read-only-ness*, **never correctness/cost.** That AST is free fuel for pre-flight validation.
- **The chokepoint + caps:** `src/db.py` `run_select` ← `assert_safe_select`; `SafetyLimits` caps rows/time/size. `/execute` is **synchronous** today — a legitimately long query times out the HTTP request.
- **Curated-metadata precedent:** the EBS packs + glossary (`src/core/ebs_packs.py`, ADR-015) prove the opt-in, names/descriptions-only context pattern a value-domain glossary would follow.
- **Single-worker / ephemeral-storage posture:** RISK-16 (single worker) + ITM-019 (ephemeral storage) — which is **why** the async job store + result cache are designed **in-memory, single-worker, short-TTL** (consistent with D-B), not a durable queue.
- **Greenfield (confirmed absent):** index/partition/stats/cardinality profiling, plan-aware prompt context, static cost heuristics, async/job execution, server-side statement timeout/cancellation, result caching, local value-domain resolution, self-heal retry, plan reading.

## Non-negotiables (the five invariants — must not regress)
1. **SELECT/CTE-only chokepoint** — unchanged. Profiling queries are SELECTs over `ALL_*` catalog views through the existing chokepoint. Async execution runs the **same** approved SELECT through `run_select`; it changes *when/how we wait*, not *what runs*. Any plan-reading diagnostic is a **separate, explicitly-guarded read-only path**, never user SQL widening the chokepoint.
2. **AI proposes / user approves** — preserved. Plan-aware generation only changes the **context** the model sees; the proposal is still reviewed/approved (Auto-run governs as today). Self-heal re-routes a rewrite **through the same review gate** — no silent re-execution.
3. **Schema-names-only to the LLM / no row data to any model** — preserved and **hardened**. Enriched profile metadata sent to the model is **names/structure/statistics only** (index column *names*, partition *key names*, row-count *magnitudes*, cardinality *flags*) — never row values. **Value domains are resolved 100% locally (D-C); distinct values never reach the model.** The `assert_no_values` tripwire covers the enriched context as a whole.
4. **No client-side DB secrets** — preserved. Connections by `profile_id`; job handles are opaque ids; the in-memory result cache holds already-authorized result data keyed by profile, never credentials.
5. **Sanitized errors with `error_id`** — preserved. Timeouts, cancellations, profiling-privilege failures, and job errors all surface through the existing `friendlyError`/`errorMessage` + `_db_error` policy ([ADR-024](../adr/ADR-024-user-readable-error-presentation.md)); raw ORA/driver text is logged server-side only.

## Objectives
1. **Profile the client database read-only** at onboarding to capture the metadata that actually moves accuracy + performance: indexes, partition keys, row-count magnitudes, precise types + nullability, PK/unique, and FK **cardinality** — sampled, bounded, privilege-degrading. From that same profile, produce an **advise-only Optimization Advisory** (D-K) for the implementation engineers — recommended structural DDL the app **never executes**.
2. **Plan-aware generation:** feed the model a compact **performance brief** (fact vs lookup sizes, indexed/partitioned columns, cardinality-annotated join graph) + fix the **12k truncation** via relevant-subset selection, so it writes queries that filter/join on what's indexed/partitioned and order joins sensibly.
3. **Invariant-safe accuracy:** resolve the `status='A' not 'Active'` class of silent failures by **local literal mapping** — the model emits a bind, we map the user's word to the real literal from a server-side domain — **with no values ever sent to the model**.
4. **Resilient execution:** a long query no longer times out the request — it runs as an **async job** (submit → `job_id` → poll → fetch) with a **server-side statement timeout, cancellation, row cap, and an ephemeral in-memory result cache**, plus an opt-in **sample-first** approximate preview for huge tables.
5. **Pre-flight + self-heal (lightweight):** always-on **static** AST heuristics warn on cartesian / unaggregated-fact-scan / missing-partition-predicate before run; on a timeout/optimizable error, offer a **bounded model rewrite** routed back through the review gate (no rows to the model).
6. Make the enriched metadata + human semantics a **required onboarding step** (D-L): a setup readiness gate that won't mark a connection "ready for CXO use" until profiling succeeds (or is explicitly resolved) and the human-supplied semantics — glossary, value domains, undeclared-FK joins — are captured.
7. Keep it governed: charter → owner decisions → design (ADR-028…031) → build B1…Bn (each review-gated + HOLD-for-sign-off) → independent exit-gate review (reviewer ≠ author).

## Architecture sketch
```
ONBOARDING (Pillar 1a — profiling)
  profile a connection ──SELECT-only via chokepoint──▶ ALL_INDEXES / ALL_IND_COLUMNS /
     ALL_PART_KEYS / ALL_TAB_COLUMNS / ALL_TABLES.NUM_ROWS / ALL_CONSTRAINTS
        └─ enriched metadata (additive on the schema record) + server-side value domains
           (bounded, sampled, privilege-degrading)            [no row data leaves the server]

ASK (Pillar 1b — plan-aware generation + accuracy)
  question + enriched schema ──▶ relevant-subset select (fixes 12k truncation)
        └─ performance brief + cardinality-annotated join graph  ──▶ NL→SQL (names/structure/stats only)
              └─ proposed SQL ──▶ static pre-flight heuristics ──▶ review (approve)
                    └─ local value-domain resolution: "active" → bind 'A'   [no values to model]

RUN (Pillar 2 — resilient execution)
  approved SQL + binds ──▶ /execute (hybrid)
        ├─ fast  → synchronous result (≤ server timeout)
        └─ slow  → async job (job_id) → poll → fetch     [statement timeout + cancel + caps]
              └─ ephemeral in-memory result cache (SQL+binds+profile, short TTL)
        (opt-in) sample-first preview: SAMPLE(n) approximate → one-click full/async run

SELF-HEAL (D-H, bounded)
  timeout / optimizable ORA error (sanitized, no rows) ──▶ model rewrite ──▶ re-approve (review gate) ──▶ /execute
```
Every SQL hop is the existing chokepoint; the model only ever sees names/structure/statistics; no row data leaves the server to any model on any path.
